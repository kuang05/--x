# 架构决策记录（ADR）

每条记录：**背景 → 决策 → 后果 → 被否方案**。只写会影响后续维护成本的决定，不写"用了 SQLite"这种默认事实。

---

## ADR-01 单库（app.db）而不是每工程一库

- **背景**：PRJ-002 要"最近工程列表"，DAT-004 要跨工程去重，PRJ-006 要跨机导入。
- **决策**：全部工程放一个 `app.db`，大文件走文件系统 CAS `blobs/ab/cd/<sha256>`。
- **后果**：最近工程、跨工程去重都变成单表查询；坏处是单库损坏影响全部工程，必须 WAL + 迁移前备份 + 定期 `VACUUM INTO` 快照。
- **被否**：每工程一库。ATTACH 跨库事务、跨工程去重、最近列表都要额外机制，复杂度更高。

## ADR-02 主键用 UUIDv7 文本

- **背景**：工程包要跨机器导入（PRJ-006），历史不可篡改（DAT-002）。
- **决策**：业务表统一 `id TEXT`（36 字符 UUIDv7），自增整型只用于纯日志表。
- **后果**：导入不需要重编 ID；时间有序，索引局部性好；代价是索引比整型大约 2.25 倍。`slice_path` 是唯一例外（整型行号），因为单切片可达数万段。
- **被否**：自增整型（导入必冲突）、业务复合键（重命名会级联改主键）。

## ADR-03 当前工作集 + 对象级版本差异

- **背景**：一块板 20 万面，不能每版存全量；58 张表也不该每行带 `version_id`。
- **决策**：业务表只存当前状态；历史 = `version_item`（对象级差异）+ `blob`（几何快照）+ `snapshot`（周期恢复点）。
- **后果**：版本回溯需要"从最近快照重放差异"，实现复杂度集中在版本模块；换来存储与查询的常数级开销。
- **被否**：全量快照（存储爆炸）、多版本行（查询必须带版本条件，任何漏写都会读到脏数据）。

## ADR-04 双哈希：content_hash 与 file_hash

- **背景**：G-code 文件里通常带时间戳，"字节哈希相同"永远不成立，但验收要求"两次导出哈希一致"。
- **决策**：`gcode_export` 同时存规范化内容哈希与落盘字节哈希，**验收只看前者**。规范化规则：剔除时间戳/会话 ID/绝对路径，浮点统一 `%.3f`，字段顺序固定。
- **后果**：T16/T20/AGT-008 三处验收才有意义；实现侧必须有一份规范化器，且改动它等于改哈希口径，需版本化。
- **被否**：只存 file_hash（验收恒假）、只存内容哈希（无法排查文件损坏）。

## ADR-05 拆表 vs JSON 的判定标准

- **背景**：工艺参数、计划步骤参数、G-code 头都是"一坨结构"，全拆表会膨胀，全塞 JSON 又查不动。
- **决策**：满足任一即拆表 —— ①出现在验收查询/筛选/排序里；②需要被其他行外键引用；③需要逐项更新或逐项 diff。全部满足才落 JSON —— 整体读写、无跨行引用、无按字段查询、diff 粒度接受整块替换。
- **后果**：`mrc_issue`/`slice_path`/`pad` 拆表；`process_profile.params_json`、`plan_step.params_json`、`gcode_export.header_json` 留 JSON。
- **被否**：全部 EAV（查询与约束都失控）、全部 JSON（外键与索引失效）。

## ADR-06 分数属于 mrc_run，不属于 version

- **背景**：MRC-011 要求"改阈值重新评分，旧记录不被覆盖"。
- **决策**：`mrc_run` 只追加，五元唯一 `(version_id, rule_version_id, tool_geometry_id, engine_version, input_digest)`；`version.score_before/after` 只是提交瞬间快照。
- **后果**：重评分不产生新版本（设计没改），N:1 关系天然成立；`mrc_issue` 冗余版本与规则版本换热索引。
- **被否**：分数存 version（重评分 = 修改历史行，触发器会拦住）、分数存单独一张表但按项目聚合（丢失规则版本维度）。

## ADR-07 追溯闭包用冗余列 + 触发器，而不是全靠 join

- **背景**：缺陷要能回到"哪一版、哪一批、哪一刀"，但列表页不能每次三跳 join。
- **决策**：`defect` 固化 `print_job_id`/`slice_set_id`/`design_version_id`；`attribution` 独立成表记录归因与复议。
- **后果**：列表页单表过滤；写入时多一次触发器校验（成本极低）；历史归因不随切片漂移。
- **被否**：只存作业（归因漂移）、归因塞进 defect（复议会覆盖历史）。

## ADR-08 重放 = 回放 tool_call，不重新推理

- **背景**：AGT-008 要求"同一计划、同一起始版本、同一工具版本，重放后 G-code 哈希一致"，而 LLM 推理本身不可复现。
- **决策**：`plan_step.params_json` 存**解析后的具体命令**（含对象 ID）；`replay_run` 记录七要素（起始版本+摘要、工具链版本、规则版本、工具几何、工艺配置+哈希、材料批次、随机种子）。
- **后果**：断网也能重放（AGT-010）；`model_id`/`prompt_digest` 只做审计，不参与一致性判定。
- **被否**：重放时重新调用模型（不可能 100% 一致）、只存自然语言意图（无法执行）。

## ADR-09 作业状态用 status + phase 双字段

- **背景**：PRT-003/004 要求区分"打印中暂停"与"固化中暂停"，两者恢复算法完全不同。
- **决策**：`print_job.status`（created/running/paused/…）+ `print_job.phase`（idle/printing/curing/cooling）；暂停详情落 `print_interruption`，含 `temp_at_c`、`remaining_hold_s`、`resume_decision`。
- **后果**：固化中断必须 `recompute_hold`，禁止直接续时，可用 CHECK 约束兜住。
- **被否**：单字段塞 12 个状态（"暂停"丢失阶段信息，恢复逻辑只能猜）。

## ADR-10 枚举存 code，中文标签进字典

- **背景**：UI-008 要求中文界面，但数据库存中文枚举会让排序、迁移、外部对接都变难。
- **决策**：库里只存英文 code，`dictionary_entry` 提供 `label_zh`/`description`，兼作错误码解释与术语表。
- **后果**：UI 层必须做一次映射；换来的是枚举可扩展、可检索（FTS5）、错误信息不会以内部代号示人。
- **被否**：直接存中文（迁移与大小写/空格问题）、枚举表每类一张（几十张小表）。

## ADR-11 PostgreSQL 的循环外键用 ALTER 追加

- **背景**：`project.current_version_id ↔ version.project_id` 构成环；SQLite 容忍前向引用，PG 不容忍。
- **决策**：生成器做环检测，把闭环边改为 `ALTER TABLE ... ADD CONSTRAINT` 并在建表后追加；其余外键内联；表按拓扑序创建。
- **后果**：两份 DDL 语义一致；PG 侧多一步，但可重复执行（首建时）。
- **被否**：去掉 `current_version_id` 外键（丢失引用完整性）、改成可空且不建外键（同前）。

## ADR-12 用代码生成四份产物，而不是手写

- **背景**：ER 图、DDL、字典、追溯矩阵四份文档最容易"改一处忘三处"。
- **决策**：`schema/*.py` 为唯一事实源，`tools/gen_*.py` 生成；生成物顶部标注"勿手改"。
- **后果**：模型变更成本从"改 4 处"降到"改 1 处 + 跑 4 条命令"；代价是生成器本身要维护，且 Python 定义的可读性要刻意经营（中文注释、按域分文件）。
- **被否**：手写 Markdown + 手写 DDL（本项目 58 张表，手写必然漂移）、直接用数据库反向生成文档（DDL 会变成事实源，丢失需求追溯）。
